Reference · UML class · dotfiles installer

One Python installer for Linux, macOS and Windows

Object model for install.py. Three layers are separated by contract: strategy (how a link is made), orchestration (what the installer does), services (state, filesystem, reporting). Every OS difference in link creation lives behind Linker; per-OS config selection is data-driven through VariantLinkSpec and VariantLinkTask.

1 · Strategy layer — how a link is made

The only place that knows about symlinks, junctions and copies. LinkerFactory probes the host once at start-up and returns the strongest strategy the machine can actually perform, so no caller ever branches on os.name.

2 · Orchestration layer — tasks

Installer owns an ordered list of tasks and knows nothing about symlinks. LinkTask handles normal manifest entries. VariantLinkTask handles per-OS selector entries. Cleanup and git-reset tasks are listed in the inventory.

3 · Per-OS variant data

VariantLinkSpec carries the per-OS source map and selector filename as data. VariantLinkTask resolves the current platform and delegates to Linker. Manifest owns both normal LinkSpec entries and VariantLinkSpec entries.

4 · Service layer — state, filesystem, reporting

Plain, injectable collaborators. FileSystem is the test seam: swap it for an in-memory fake and the whole installer runs without touching a real home directory.

5 · Full class inventory

Classes in install.py. Dataclasses and small ABCs keep the object count cheap; each class has one reason to change.

Design rule: no class knows both what to install and how to link. Manifest decides what, Linker decides how, Installer sequences, and every layer can be tested alone.

Windows linking, measured on this machine: a directory becomes an NTFS junction (mklink /J), which needs no permission. A file becomes a real symlink, which needs Developer Mode. Without it the installer copies the file and says so.
